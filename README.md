# QA Navigator

Клиентское React-приложение для анализа требований, применения техник тест-дизайна,
ведения чек-листов и тест-кейсов, подготовки баг-репортов, тестовых данных и релизных
отчётов. Часть сценариев может использовать OpenRouter или Google Gemini; рабочие
данные сохраняются в `localStorage` браузера.

## Запуск

Требования: актуальная LTS-версия Node.js и npm.

```bash
npm install
npm run dev
```

Проверка production-сборки:

```bash
npm run build
```

> API-ключи вводятся в интерфейсе и сохраняются в `localStorage`. Не используйте
> ключи с избыточными правами или без лимитов. Текст AI-запросов передаётся выбранному
> внешнему провайдеру, поэтому не отправляйте секреты и персональные данные.

## Результаты технического аудита

### Сильные стороны

- Продукт закрывает связный QA-процесс: требования → тест-дизайн → выполнение →
  дефекты → итоговый отчёт, а также содержит самостоятельную базу знаний.
- Есть полезные локальные алгоритмы (pairwise/IPOG, классы эквивалентности,
  граничные значения, таблицы решений и переходы состояний), не зависящие от AI.
- Поддержаны светлая/тёмная темы, адаптивная навигация, экспорт документов и
  резервное копирование пользовательских данных.
- Данные типизированы TypeScript-интерфейсами, а ошибки сети от AI-провайдеров
  преобразуются в понятные диагностические сообщения.

### Найденные и исправленные проблемы

1. **Stored/remote XSS в предпросмотре Markdown.** Ответ AI попадал в
   `dangerouslySetInnerHTML` без экранирования. Теперь входное содержимое сначала
   экранируется, и только затем к нему применяется ограниченная Markdown-разметка.
2. **Неочевидная подмена AI-провайдера.** При выбранном Gemini без Gemini-ключа код
   мог использовать OpenRouter. Теперь наличие ключа проверяется именно для выбранного
   провайдера, а ошибка называет его явно.
3. **Слабые идентификаторы.** Короткий идентификатор на базе `Math.random()` мог
   столкнуться при росте данных. Используется `crypto.randomUUID()`.
4. **Неполная и небезопасная резервная копия.** Экспорт не включал анализ требований,
   а импорт принимал произвольные имена ключей `localStorage` и скрывал ошибки.
   Теперь экспорт и очистка используют единый allowlist, импорт проверяет структуру
   и показывает ошибку пользователю.
5. **Ошибочное обещание конфиденциальности.** Интерфейс утверждал, что данные никогда
   не покидают браузер, хотя AI-запросы отправляются третьей стороне. Текст уточнён.
6. **Мусор сборки в Git.** Добавлен `.gitignore` для `node_modules`, `dist` и локальных
   файлов.

### Недостатки и технический долг

- `App.tsx` и `handbook-data.ts` — монолиты примерно по четыре тысячи строк. Это
  повышает стоимость ревью, тестирования и повторного использования.
- В репозитории лежит сгенерированный набор UI-компонентов, который приложение не
  импортирует. Из-за него `package.json` содержит десятки фактически неиспользуемых
  зависимостей Radix/MUI/форм/графиков. Удалять их следует отдельным изменением после
  проверки планов дизайна.
- Нет unit-, component- и end-to-end-тестов, линтера, отдельного `typecheck`-скрипта,
  CI и зафиксированного lock-файла. Сейчас регрессии выявляет только сборка Vite.
- Несколько AI-сценариев всё ещё подавляют исключения пустым `catch`, поэтому
  пользователь не всегда видит причину сбоя. JSON AI-ответов проверяется приведением
  типов, а не runtime-схемой.
- API-ключи доступны любому JavaScript-коду на origin через `localStorage`. Для
  production нужен backend/BFF; клиентское хранение допустимо только как явно
  обозначенный локальный режим.
- Production bundle предупреждает о JS-чанке больше 500 kB, а пять PNG из справочника
  занимают примерно 9 MB без оптимизации и lazy loading.
- Рендерер Markdown самописный: после устранения XSS он безопаснее, но неполно
  поддерживает таблицы/списки и не имеет тестового набора.
- Состояние активного раздела не отражено в URL, поэтому нет deep links, истории
  браузера и восстановления маршрута после обновления.
- Доступность неполна: часть icon-only кнопок не имеет `aria-label`, модальные окна
  не управляют фокусом, tooltip работает только мышью.

## План улучшения и доработки

### Обязательные ограничения

1. **Не ломать существующие сценарии.** Каждый этап начинается с фиксации текущего
   поведения тестами, выполняется небольшими атомарными коммитами и принимается только
   после прохождения регрессионного набора.
2. **Offline-first.** Pairwise, EP, BVA, таблицы решений, переходы состояний, ручная
   документация, справочник, импорт и экспорт должны работать без сети и API-ключей.
3. **Нулевая обязательная стоимость.** Нельзя добавлять функции, для которых необходимы
   платная подписка, платный API, коммерческая лицензия или постоянно оплачиваемый
   сервер. Допустимы только open-source зависимости и бесплатные локальные инструменты.
4. **AI только как опция.** OpenRouter/Gemini нельзя считать гарантированно бесплатными:
   тарифы и лимиты меняются. Поэтому AI-функции должны иметь ручной или локальный
   fallback, явно показывать провайдера и никогда не блокировать основную работу.
5. **Обратная совместимость данных.** Нельзя менять сохранённые структуры без версии,
   миграции, резервной копии и теста чтения данных предыдущей версии.
6. **Одна актуальная реализация.** Новая реализация полностью заменяет старую; нельзя
   оставлять рядом `Old`, `Legacy`, `V2`, закомментированные копии или два маршрута к
   одной функции.
7. **Лимит размера модуля.** Цель — до 700 строк, жёсткий максимум — 800 строк с
   учётом комментариев. Проверка `max-lines` должна выполняться в lint/CI. Исторические
   монолиты `App.tsx` и `handbook-data.ts` являются временным исключением только на
   период декомпозиции: добавлять в них новые функции запрещено, каждый затрагивающий
   их PR обязан уменьшать их размер.
8. **Повторное использование без god-utils.** Повторяющаяся логика выносится в модуль
   по ответственности (`hooks`, `lib`, `domain`, `features`), но несвязанные функции
   не складываются в общий `utils.ts`. UI-компонент остаётся рядом со своей feature,
   пока его действительно не используют как минимум два независимых модуля.

### Нулевой этап — защитная сетка (P0, 1 спринт)

- [ ] Зафиксировать в `docs/baseline.md` все пользовательские сценарии и ожидаемые
  результаты: запуск без ключа, локальные генераторы, документы, выполнение тестов,
  отчёт, справочник, тема, reload persistence, backup round-trip.
- [ ] Добавить строгий `tsconfig`, скрипты `typecheck`, `lint`, `test` и `test:e2e`.
  Использовать бесплатные open-source инструменты: ESLint, Vitest, Testing Library и
  Playwright.
- [ ] Добавить CI на бесплатном для open-source/доступном Git-хостинге runner либо
  предоставить идентичный локальный `npm run verify`; внешний CI не должен быть
  условием локального запуска.
- [ ] Покрыть unit-тестами чистые алгоритмы pairwise/IPOG, EP, BVA и state transition,
  расчёт релизных метрик и экранирование Markdown.
- [ ] Добавить smoke E2E без реального AI: открытие каждого раздела, создание и смена
  статуса проверки, экспорт данных, переключение темы.

**Gate этапа:** `npm run verify` проходит локально; production build и все текущие
ручные сценарии совпадают с baseline. Функциональные изменения до этого gate не
объединяются.

### Этап 1 — ошибки и целостность данных (P0, 1 спринт)

- [x] Экранировать недоверенный Markdown перед вставкой в DOM.
- [x] Проверять ключ выбранного AI-провайдера и ограничить backup allowlist-списком.
- [ ] Вынести storage-адаптер с версией схемы. Перед миграцией автоматически создавать
  snapshot; при ошибке оставлять исходные данные без изменений.
- [ ] Проверять AI JSON и backup runtime-валидаторами без обязательной новой библиотеки;
  неверные элементы отклонять до обновления React state/localStorage.
- [ ] Заменить пустые `catch` единым видимым состоянием ошибки. Добавить timeout,
  отмену через `AbortController` и кнопку повтора без автоматического списания квоты.
- [ ] Сделать импорт транзакционным: validate → preview → подтверждение → запись;
  добавить тесты старого формата, повреждённого JSON, лишних ключей и больших файлов.

**Gate этапа:** backup текущей версии восстанавливается без потерь; повреждённый файл
ничего не изменяет; каждый сбой AI виден пользователю; offline-функции не обращаются к
сети.

### Этап 2 — безопасная декомпозиция монолита (P1, 2 спринта)

Декомпозиция выполняется **по одному модулю**. В одном коммите компонент переносится
без изменения поведения, в следующем — улучшается. Старый код удаляется в том же
коммите, где подключён новый, чтобы не существовало двух вариантов.

- [ ] Вынести `domain/types`, `storage`, `ai`, `markdown` и чистые генераторы, сохранив
  публичные интерфейсы и storage keys.
- [ ] По очереди перенести feature-модули: requirements → test-design → execution →
  reports → automation → handbook → documentation → settings.
- [ ] Ввести reducer/store только после characterization-тестов. Сохранить порядок,
  статусы, экспорт и восстановление существующих сущностей.
- [ ] Добавить error boundary вокруг каждого раздела, чтобы ошибка одной функции не
  делала приложение недоступным целиком.
- [ ] После анализа импортов удалить неиспользуемые UI-компоненты и зависимости одним
  отдельным коммитом; сравнить build и пройти полный smoke до и после удаления.

**Gate этапа:** все baseline/E2E-тесты проходят, ключи `localStorage` и backup schema
совместимы, нет файлов/экспортов с суффиксами `old`, `legacy`, `copy` или `v2`.

### Этап 3 — бесплатный AI и ручные fallback-сценарии (P1, 1–2 спринта)

- [ ] Для каждой AI-кнопки добавить полноценный ручной сценарий и шаблон: анализ
  требований, чек-лист, тест-кейс, баг-репорт, автотест и итоговый отчёт.
- [ ] Создать единый provider adapter. Реальные OpenRouter/Gemini проверки запускать
  только вручную с пользовательским ключом; автоматические тесты используют локальный
  mock и не расходуют лимиты.
- [ ] Добавить режим «Без AI» по умолчанию и явное согласие перед отправкой текста
  внешнему провайдеру; показывать, какие данные будут переданы.
- [ ] Опционально исследовать локальные WebLLM/Ollama-адаптеры, но не включать модель
  в основной bundle и не требовать мощного устройства. Это enhancement, не зависимость.
- [ ] Не добавлять платный BFF. Если proxy понадобится для CORS, предоставить
  open-source self-hosted вариант и сохранить полностью рабочий клиентский/offline
  режим без него.

**Gate этапа:** полный QA-flow завершается без ключа; тесты не выполняют внешние
запросы; отключение/исчерпание бесплатной квоты не приводит к потере данных.

- [ ] Добавить URL-навигацию по разделам после E2E-фиксации текущего поведения; старые

**Gate этапа:** initial JS меньше согласованного бесплатного bundle budget, изображения

## Матрица регрессии перед каждым merge

| Проверка | Команда/метод | Обязательность |
|---|---|---|
| Формат и типы | `npm run lint && npm run typecheck` | каждый PR |
| Unit/integration | `npm test` | каждый PR |
| Production bundle | `npm run build` | каждый PR |
| Offline smoke | `npm run test:e2e` с заблокированной сетью | каждый PR |
| Backup совместимость | fixtures текущей и предыдущей схемы | storage PR |
| Реальный бесплатный AI | ручной opt-in smoke без секретов в логах | provider PR |
| Accessibility/visual | axe + screenshots основных экранов | UI PR |

Пока эти скрипты ещё не добавлены, обязательный минимум — `npm run build`,
`git diff --check` и ручной проход затронутого сценария по baseline. Отсутствующая
проверка не считается успешной: она фиксируется как блокер, а не пропускается молча.

## Стратегия изменений и разрешения конфликтов

Чтобы при объединении не приходилось сохранять «оба варианта»:

- один PR меняет один feature/слой и не смешивает перенос, форматирование и новое
  поведение;
- перед началом работы ветка обновляется от целевой, а перед merge повторно проходит
  rebase/merge и весь `npm run verify`;
- общие контракты (`domain`, storage schema, provider interface) меняются отдельным
  первым коммитом, а потребители — последующими коммитами;
- новая реализация получает **то же каноническое имя и путь**, а старая удаляется в
  том же коммите; временные параллельные версии запрещены;
- для сгенерированных файлов и lock-файла конфликт не склеивается: файл
  регенерируется новой версией инструментов;
- при содержательном конфликте источником истины является версия из **новой feature-
  ветки после её обновления от target**. В обычном merge это `theirs`, но при rebase
  смысл `ours/theirs` меняется, поэтому нельзя выбирать флаг вслепую: нужно взять
  файл из именованной feature-ветки, затем запустить регрессию;
- `git checkout --ours .`/`--theirs .` для всего репозитория запрещён: это может тихо
  удалить независимые исправления безопасности. Правило «только новая версия»
  применяется к заменяемому модулю, а не к несвязанным файлам;
- после разрешения конфликта `rg` проверяет отсутствие conflict markers и старых
  экспортов, затем выполняется полный verify. В PR фиксируется, какой вариант стал
  каноническим.

Такой процесс гарантирует одну актуальную реализацию без ручного объединения старого
и нового кода, но не маскирует независимые изменения из целевой ветки.

## Definition of Done

Изменение готово к слиянию, только если:

- описаны затронутые сценарии и риски, добавлены/обновлены тесты;
- сохранены offline-режим, существующие данные и обратная совместимость;
- нет обязательного платного сервиса, API или коммерческой лицензии;
- нет дублирующей старой реализации и закомментированного кода;
- build, typecheck, lint, unit и релевантный E2E прошли;
- размер bundle и доступность не ухудшились без зафиксированного обоснования;
- README/ADR отражают новый канонический вариант и способ отката.
