# QA Navigator — архитектура и текущее состояние

QA Navigator — клиентское React/Vite/TypeScript-приложение для организации QA-работы, тест-дизайна, выполнения проверок, работы с тестовыми данными, SQL и обучения. Основные локальные сценарии выполняются в браузере; AI-провайдеры подключаются отдельно и не являются архитектурной основой приложения.

## Реализованные разделы приложения

Навигация в `src/app/domain/navigation` и композиция в `src/app/App.tsx` включают:

1. **Рабочее пространство проектов** — создание проектов и выбор активного проекта; внутри проекта доступен Test Management: тест-кейсы, наборы, планы/прогоны, история, дефекты и базовые коллекции шаблонов. Данные TMS разделены по проектам, входят в общую резервную копию и поддерживают отдельный проверяемый JSON-архив проекта с импортом в выбранный проект.
2. **Мастер для новичка** — пошаговая помощь и rule-based рекомендации.
3. **Анализ требований** — работа с требованиями и AI-assisted сценарии.
4. **Тест-дизайн** — Pairwise/IPOG, классы эквивалентности, BVA, таблицы решений и переходы состояний.
5. **Выполнение тестов** — чек-листы, статусы, результаты и баг-репорты.
6. **Автотесты** — раздел подготовки примеров/шаблонов кода; AI-возможности зависят от выбранного провайдера.
7. **Релизный отчёт** — формирование отчёта и метрик на основе доступных QA-данных.
8. **Генератор тестовых данных** — наборы граничных, специальных, email/date и других тестовых значений.
9. **API TESTING** — API Workbench: отправка HTTP-запросов из браузера, заголовки, JSON body, переменные окружения, базовые assertions по статусу/содержимому ответа, просмотр response/status/headers, cURL и локальная история с маскированием секретов. Реальный доступ зависит от CORS и сетевой политики endpoint.
10. **DATABASE & SQL** — отдельный пункт бокового меню, открывающий страницу «Работа с базами данных». Внутри доступны конструктор запросов, «Шпаргалка SQL» и отдельная вкладка «Частые SQL-запросы для QA» с готовыми проверками данных. Выполнение происходит в браузерной SQL-среде на базе `sql.js` (SQLite/WASM), а не через прямое подключение к PostgreSQL/MySQL; SQL-тренажёра с заданиями нет.
11. **BACKEND & LOGS** — локальный анализ выбранных log/text/JSON/JSONL/CSV-файлов, фильтрация, группировка ошибок, request/trace ID и CSV export. Файлы не отправляются на сервер.
12. **ИНТЕГРАЦИИ** — обмен Postman Collection и Environment JSON с сохранением исходной структуры, импорт OpenAPI 3.x YAML/JSON с разбором операций и официальные ссылки на внешние сервисы. Прямые коннекторы остаются будущими задачами.
13. **База знаний QA** — справочник, поиск, фильтры и закладки.
14. **Learning Mode** — учебные модули, уроки, инфографики, отметки прогресса и навигация.
15. **Документация** — создание и экспорт QA-документов.
16. **Настройки** — тема, язык, AI-провайдеры, резервное копирование и импорт/экспорт.

Состав и фактическое поведение разделов следует сверять с `src/app/App.tsx`, feature-модулями и `package.json`; этот документ не является обещанием функций, которых ещё нет.

## Архитектурные слои

- `src/app/domain` — общие доменные типы, навигация и модели проектов.
- `src/app/core` — AppContext, storage, валидаторы, конфигурация, i18n и AI-адаптер.
- `src/app/components` — общие UI-компоненты.
- `src/app/features/<feature>` — функциональные разделы приложения.
- `src/app/handbook-*` — контент базы знаний и учебной программы.
- `src/app/hooks` — React hooks.
- `src/app/lib` — небольшие технические адаптеры.

`App.tsx` композирует навигацию, глобальное состояние и feature-модули. Новую бизнес-логику следует размещать в соответствующей feature/domain/core области, а не возвращать в App.

## Технологии и хранение

- React + TypeScript + Vite.
- `sql.js` — SQLite, скомпилированная в WebAssembly, для браузерного Database Workbench.
- Основные пользовательские данные приложения используют существующие localStorage-контракты. Test Management использует обратимое хранилище: IndexedDB по умолчанию и прежний localStorage как доступный режим возврата. Миграция сохраняет legacy-копию; вложения хранятся в IndexedDB. Общая резервная копия включает TMS и вложения, а отдельный JSON-архив переносит проект между браузерами/устройствами. Сервер для хранения QA-данных не используется. История API Workbench входит в allowlist резервной копии и проходит отдельную проверку структуры; чувствительные значения маскируются перед сохранением.
- Существующие storage keys и формат резервной копии являются контрактом обратной совместимости. Изменения требуют версии схемы, миграции, backup и тестов.

## AI и обязательная автономность

В текущей реализации предусмотрены внешние AI-провайдеры OpenRouter и Gemini, пользовательские API-ключи хранятся в браузерном хранилище. Это означает, что AI-запросы передают выбранные данные внешнему провайдеру.

Целевое правило продукта: **ни одна основная функция не должна требовать API-ключа**. AI может быть только необязательным дополнением. Для каждой AI-assisted функции необходимо обеспечить рабочий локальный, rule-based или ручной fallback. Не обещать, что бесплатная квота облачного AI будет постоянной.

## Целевая продуктовая концепция

Бесплатное браузерное рабочее пространство для ручного тестирования, API, SQL-проверок, диагностики backend и обучения QA.

Полный целевой blueprint, интеграционная стратегия, границы браузерной архитектуры и будущие этапы описаны в [docs/PRODUCT_BLUEPRINT.md](docs/PRODUCT_BLUEPRINT.md).

## Правила разработки

- Не изменять `main` напрямую; работать в выделенных feature/refactor/docs ветках.
- Сохранять существующее поведение и пользовательские данные.
- Не создавать параллельные `Old`, `Legacy`, `V2`, `Copy` реализации.
- Жёсткий максимум исходного `.ts/.tsx` файла — 1500 строк.
- Новые зависимости должны быть бесплатными и иметь совместимую open-source лицензию.
- Не вводить обязательный платный backend, API, регистрацию или AI.
- Перед PR выполнять `npm run verify`; не считать непроверенный этап завершённым.
