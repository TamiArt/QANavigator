# Test Management — спецификация QA Navigator

## Цель и ориентиры

Встроенная TMS объединяет лучшие продуктовые паттерны TestRail и Test IT: структурированную библиотеку тестов, повторное использование сценариев, планы и прогоны, результаты, дефекты, traceability, историю, аналитику и командную работу. Это единый контур внутри каждого проекта QA Navigator. Мы заимствуем подходы, но не копируем интерфейсы, тексты или закрытую реализацию поставщиков.

## Реализованный первый срез

Путь: Рабочее пространство → выбранный проект → Test Management.

Вкладки:
- Обзор — счётчики тест-кейсов, наборов, планов, прогонов и дефектов.
- Тест-кейсы — создание, поиск, ключ, папка, предусловия, шаги, ожидаемый результат, приоритет; выбор кейсов для набора.
- Наборы (Test Suites) — создание набора из выбранных кейсов; удаление набора не удаляет кейсы.
- Планы и прогоны (Test Plans / Runs) — план с окружением и составом кейсов, запуск, статусы Passed / Failed / Blocked / Skipped, actual result, история.
- Базовые коллекции — импорт шаблонов в библиотеку проекта как редактируемых копий.
- Дефекты — реестр дефектов с ключом, severity, priority, status и связью с тест-кейсом.

### Стартовые коллекции

1. Smoke / критический пользовательский путь.
2. Авторизация и регистрация.
3. Формы и валидация.
4. CRUD и управление данными.
5. Поиск, фильтры и таблицы.
6. API: базовый контракт.
7. Мобильное приложение.
8. Безопасность и доступы.
9. Доступность и UX.
10. Регрессионный набор.

Шаблоны — отправная точка, а не универсальные обязательные требования. QA адаптирует предусловия, тестовые данные и expected result к конкретному продукту.

### Хранение

- Данные разделены по projectId, ключ qa_navigator_test_management_v1.
- Ключ включён в общую резервную копию Settings и проверяется при импорте.
- Доступен JSON-экспорт и импорт архива выбранного проекта. Импорт валидирует структуру и связи, затем переносит данные в текущий проект, не меняя его ID.
- Общая резервная копия приложения продолжает включать ключ Test Management.
- Основные операции не требуют AI, API-ключа или backend.
- Структурированные данные TMS находятся в хранилище текущего профиля браузера. Для TMS доступны IndexedDB (основной режим) и localStorage (предыдущий режим); переключение между ними доступно в интерфейсе. Первая миграция в IndexedDB выполняется однократно, копия localStorage не удаляется. При возврате данные копируются обратно; если localStorage не принимает весь объём, переключение не выполняется. Если IndexedDB недоступен, можно явно открыть сохранённую legacy-копию, не удаляя IndexedDB.
- Бинарные вложения хранятся в отдельном object store IndexedDB и привязываются к кейсам, результатам прогонов и дефектам. Максимальный размер файла — 20 МБ, размер вложений в архиве проекта — до 50 МБ.
- Архив проекта содержит данные, вложения и проверку ссылочной целостности; импорт заменяет данные только выбранного проекта. Пользователь сохраняет архив на компьютере и переносит его между браузерами/устройствами.
- Общая резервная копия приложения включает данные TMS и бинарные вложения (до 100 МБ суммарно); восстановление использует текущий выбранный режим хранилища.
- Это local-first режим одного браузерного профиля; совместная синхронизация и роли не реализованы. Очистка данных браузера без резервной копии может привести к потере локальных данных.

## Целевая функциональность полноценной TMS

### Библиотека тестовой документации
- Дерево папок с вложенностью, drag-and-drop, фильтры, теги, компоненты, полнотекстовый поиск.
- Редактор кейса: описание, предусловия, шаги с expected на каждом шаге, тестовые данные, постусловия, приоритет, тип, теги, automation status, effort estimate, external references, связи с требованиями и переиспользуемыми общими шагами.
- Shared Steps library: общие шаги можно редактировать и подключать к нескольким кейсам; при запуске они разворачиваются в неизменяемый снимок выполнения.
- Версии и история изменений с восстановлением старой версии как новой; архивирование и клонирование. Сравнение сохранённой версии с текущей доступно в истории; массовое перемещение по папкам, смена приоритета и архивирование доступны для выбранных кейсов.
- Поиск, фильтрация по папкам/приоритету, иерархические пути папок через разделитель `/`.
- Shared steps, параметры, data-driven кейсы, чек-листы, BDD/Gherkin и exploratory charters.

### Test Suites и Test Plans
- Иерархические и динамические suites.
- План с релизом/build, окружением, scope, целями, рисками, ответственными, датами, entry/exit criteria.
- Фиксированный snapshot состава и конфигурации плана (окружение, релиз, build, критерии) на момент запуска.
- Платформы, конфигурации, регионы и роли.
- Повторный запуск failed/blocked, rerun выбранных кейсов и сравнение прогонов.

### Test Runs и выполнение
- Not Run, Passed, Failed, Blocked, Skipped, Retest, In Progress.
- Результат на уровне каждого шага, общий actual result и статусы выполнения.
- Скриншоты, видео, HAR, логи и другие файлы можно прикреплять к кейсам, результатам прогонов и дефектам.
- Создание дефекта из failed результата с заполнением исходного кейса, прогона, шагов, expected/actual.
- Аудит событий, временные метки, история статусов и повторное открытие.
- Офлайн-черновики и восстановление незавершённого прогона.

### Дефекты
- Карточка: summary, описание, шаги, expected/actual, environment/build, severity, priority, assignee, labels, attachments.
- Жизненный цикл New → Open → In Progress → Fixed → Retest → Closed / Reopened / Rejected.
- Связи с кейсами и прогонами; severity, priority, environment, assignee, labels, вложения.
- Комментарии и локальная история смены статуса. Дедупликация и расширенные фильтры остаются в backlog.

### Requirements Traceability
- Реестр требований, описания и критерии приёмки.
- Связь Requirement ↔ Test Case; отчёт о покрытии и список непокрытых требований.
- Автоматический impact analysis и полная цепочка Requirement ↔ Run ↔ Defect остаются в backlog.
- Метрики покрытия рассчитываются по актуальным связям.

### Аналитика и отчёты
- Метрики последнего прогона: pass rate, Passed/Failed/Blocked/Skipped/Not Run; покрытие требований, автоматизации и открытые дефекты.
- CSV-экспорт матрицы трассировки и результатов прогона.
- Тренды между релизами, flaky/reopened tests, длительность, aging и PDF/HTML отчёты остаются в backlog.

### Командная работа
- Роли Owner, Admin, QA Lead, Tester, Viewer и granular permissions.
- Исполнители/reviewers, комментарии, упоминания, уведомления.
- Optimistic locking/conflict resolution, audit log.
- Интеграции issue trackers и CI.
В выбранном browser-only режиме командная синхронизация, серверные роли и одновременная работа нескольких пользователей не входят в реализацию. Они намеренно исключены, чтобы не вводить backend, аккаунты и обязательные расходы.

### Импорт, экспорт и интеграции
- CSV импорт/экспорт тест-кейсов с распространёнными заголовками TestRail-style и Test IT-style (Title/Name, Section/Folder, Preconditions, Steps, Expected Result, Priority, Labels/Tags, References, Automation Type, Estimate); CSV-экспорт результатов и трассировки.
- JUnit XML import с сопоставлением testcase по ключу или названию в выбранном плане.
- JSON-архив проекта с вложениями и общая резервная копия приложения.
- Полное XLSX, JUnit XML и точные миграционные адаптеры TestRail/Test IT с preview/mapping остаются в backlog; их нужно реализовывать по реальным образцам экспортов.

## Целевая доменная модель

Сущности: Project, Folder, TestCase, TestStep, SharedStep, TestSuite, TestPlan, TestRun, TestResult, Attachment, Requirement, Defect, Comment, User, Role, AuditEvent, Release, Environment.

Все записи имеют стабильный ID, projectId и timestamps. История прогона должна быть воспроизводимой: Run хранит snapshot кейса/шагов на момент запуска; редактирование исходного кейса не переписывает старые результаты.

Связи: Suite N:M TestCases; Plan N:M Suites/TestCases; Run N:1 Plan; Run 1:N Results; Result N:M Defects/Evidence; Requirement N:M TestCases; Defect N:M TestCases/Results/Requirements.

## Архитектура и миграции

1. Структурированные данные TMS по умолчанию хранятся в IndexedDB; legacy localStorage мигрируется однократно и не удаляется. Пользователь может переключить режим хранения из интерфейса. Перед записью проверяется структура и проектная целостность; повреждённые исходные данные блокируют миграцию, а не превращаются молча в пустой список.
2. Поддерживать schemaVersion и последовательные миграции без потери существующих backup formats.
3. Добавить валидаторы сущностей и ссылочной целостности.
4. Атомарно обновлять прогон и связанные результаты через транзакции.
5. Project archive включает вложения и проверку ссылок/владельцев/размеров; manifest, checksum, preview и conflict resolution остаются улучшениями.
6. Сохранить local-first/offline режим; синхронизация не входит в архитектуру по умолчанию.
7. Сервер, авторизация и командная синхронизация не требуются для выбранного браузерного режима.

## Definition of Done

- Данные привязаны к проекту и переживают reload.
- Исторические результаты не меняются при редактировании кейса; запуск хранит снимок кейса и шагов.
- Backup/restore валидирует структуру, ссылки и вложения; режим localStorage доступен из интерфейса, а его исходная копия сохраняется после миграции.
- Если исходные данные повреждены или превышают квоту localStorage, переключение не должно очищать или перезаписывать IndexedDB.
- Архив проекта можно перенести на другой компьютер и импортировать в выбранный проект.
- Работа с TMS не требует серверов, аккаунта или платного облачного хранилища.
- Есть тесты доменной логики, миграций, ссылочной целостности и UI flows.
- Интерфейс доступен с клавиатуры и адаптирован к мобильному экрану.
- Browser-only ограничения описаны явно.
- npm run verify проходит до объявления этапа завершённым.
