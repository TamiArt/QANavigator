# Правило разрешения конфликтов

В проекте действует принцип **одной актуальной реализации**.

При Git-конфликте нужно:

1. определить итоговое поведение новой версии;
2. заменить конфликтующий логический блок целиком новым вариантом;
3. удалить старую реализацию и все маркеры конфликта;
4. не использовать «Accept both changes», если это оставляет две реализации;
5. выполнить `npm run verify` перед коммитом.

Названия `ours/current` и `theirs/incoming` зависят от направления merge или rebase,
поэтому выбирать вариант только по этой подписи небезопасно. Критерий выбора — именно
актуальная реализация из принимаемого изменения. Если новый вариант уже полностью
заменяет старый, старый код, старые импорты и дублирующие данные должны быть удалены.

Автоматическая проверка запрещает коммитить оставшиеся маркеры `<<<<<<<`, `=======`
и `>>>>>>>`. Git не умеет универсально определить «более новый» вариант содержимого,
поэтому полностью автоматическая стратегия выбора могла бы незаметно удалить нужный код.
